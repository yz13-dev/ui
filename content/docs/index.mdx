This registry is intentionally monochrome-first, typography-driven, and sparing with
decoration. These are the conventions new components and pages should follow.

## Markdown for AI tools

The rendered documentation has machine-readable counterparts that can be passed to
AI tools without scraping HTML:

- [`/llms.mdx/docs/content.md`](/llms.mdx/docs/content.md) — this page as processed
  Markdown, without frontmatter or MDX components
- [`/llms.txt`](/llms.txt) — a compact index of all documentation pages and their
  Markdown URLs
- [`/llms-full.txt`](/llms-full.txt) — all documentation pages combined into one
  text response

Prefer the per-page Markdown URL when only one document is relevant; use
`llms-full.txt` when the tool needs the whole design-system context.

## Typography roles

Use semantic type roles for content, not arbitrary sizes. Each role is a `--text-*`
token in `globals.css` and works as a normal Tailwind utility (`text-title`,
`text-heading-16`, ...). Weight is applied separately with `font-medium` /
`font-semibold` — the token only sets size and line-height.

| Role | Size | Use for |
| --- | --- | --- |
| `text-display` | 48px | A single page-defining statement, used rarely |
| `text-title` | 32px | The page or document title |
| `text-heading-24` | 24px | Major section breaks |
| `text-heading-20` | 20px | Nested subsection headings |
| `text-heading-16` | 16px | Component-level headings, e.g. `CardTitle` |
| `text-lede` | 17px | A short orientation paragraph under a title |
| `text-body` | 14px | Reading prose — same size as `text-sm`, more relaxed line-height |
| `text-label` | 13px | Compact names and UI labels |
| `text-caption` | 12px | Subordinate, qualifying text |

`text-sm`, `text-xs`, and the rest of Tailwind's default scale still exist and are the
right choice for dense UI chrome (buttons, inputs, badges) where control size — not
content role — should drive the type size.

## Spacing rhythm

There's no separate spacing token scale — Tailwind's default spacing multiplier
already covers it. Instead, pick the gap that matches the relationship:

- **Within a group** (label → value, icon → text): `gap-1`–`gap-2`
- **Inside a component** (padding, internal stacks — see `--card-spacing`): `gap-3`–`gap-4`
- **Between sibling components or sections**: `gap-6`–`gap-8`
- **Major page or section breaks**: `gap-12`–`gap-16`

Every gap should have one clear owner. Don't stack a parent gap with competing margins
on its children.

## Control sizes

Single-line controls use one shared density scale. The size name carries the same
height across `Button`, `Input`, `InputGroup`, `SelectTrigger`, `NativeSelect`,
`ComboboxInput`, and `InputOTP` slots.

| Size | Height | Typical use |
| --- | --- | --- |
| `xs` | 24px | Dense toolbars, compact inline actions |
| `sm` | 28px | Secondary controls and space-constrained forms |
| `default` | 32px | Standard application UI |
| `lg` | 36px | Prominent forms and primary actions |

`Textarea` uses the same names as density presets rather than fixed heights. Its
minimum heights are 48px, 56px, 64px, and 80px respectively. An `InputGroup` owns
the size of the composed control: its input, textarea, addons, icons, and nested
buttons inherit and adapt to the group size unless explicitly overridden.

Keep controls that share a row or form section on the same size. A smaller control
should communicate lower density, not compensate for a short label.

## Color

Color is a two-tier system in `globals.css`: primitive ramps, then semantic aliases
built on top of them. Components only ever consume the semantic layer.

**Primitives** are 11-step OKLCH ramps (`50`→`950`) for `primary`, `success`,
`warning`, `error`, and `info`. The achromatic `primary` ramp is pinned to pure white
at `50` and pure black at `950`; light `canvas` / `surface` and dark `canvas` use those
endpoints directly. Components consume the compact semantic palette, whose roles
select different steps from those ramps in light and dark themes. Keep raw OKLCH
values in the primitive ramps; semantic tokens should reference them with
`var(--*-*)` instead of duplicating color values.

**Semantic aliases** flip per theme and are what components actually use, as normal
Tailwind utilities:

| Utility | Source | Use for |
| --- | --- | --- |
| `bg-canvas` / `bg-surface` / `bg-muted` | `primary` ramp | Page bg, card bg, popover bg, hover/selected surfaces |
| `text-primary` / `text-secondary` | `primary` ramp | Body text hierarchy |
| `text-link` | `primary` ramp | Inline links and link-styled buttons |
| `bg-brand(-hover/-active)` / `text-brand-foreground` | `primary` ramp | Solid interactive surfaces — the default `Button`, `Badge` |
| `bg-success` / `bg-warning` / `bg-error` / `bg-info` | status ramps | Solid status surfaces |
| `text-success-foreground` / `text-warning-foreground` / `text-error-foreground` / `text-info-foreground` | status ramps | Contrast text on solid status surfaces |
| `text-success` / `text-warning` / `text-error` / `text-info` + `bg-*/10` | status ramps | Status text and soft tinted surfaces |
| `border-subtle` / `border-default` / `border-active` | `primary` ramp | Border hierarchy |

Base UI (`canvas`, `surface`, `muted`, `border`, the text hierarchy) stays
monochrome — reach for it by default. `accent` is the one deliberate chroma color in
the system and exists for meaningful emphasis only, not decoration: don't reach for it
just because it's available. `success` / `warning` / `error` / `info` are for genuine
status communication (a result, a validation state) and should pair with a non-color
cue (an icon, a label) where possible — a value isn't green just because it's
favorable.

Semantic `Button` and `Badge` variants are soft by default. Use `filled` when the
status needs stronger emphasis while keeping the same meaning:

```tsx
<Button variant="info">Learn more</Button>
<Button variant="info" filled>Review update</Button>
<Badge variant="success" filled>Active</Badge>
```

`filled` only changes `success`, `warning`, `error`, and `info`. Neutral variants
already define their own surface treatment and should not use it.

## Restraint checklist

Before shipping a component or page, check:

- No cards nested inside cards, and no border added just to patch weak hierarchy —
  prefer spacing, alignment, and type first.
- Peer elements (equivalent stats, table columns, list rows) share the same type role,
  size, and alignment. Don't resize one because its content is longer.
- Controls in the same row use the same named size; composed controls set it once on
  their root rather than restating it on every child.
- No color without meaning — a value isn't green just because it's favorable.
- No decorative gradients on backgrounds or text. The gradient-border treatment
  (`gradient-border-plugin`, used by `Button` and `Card`) is this system's intentional
  signature surface treatment, not decoration — it stays, but isn't extended to new
  uses without reason.
- Motion explains a state change or confirms an action; it doesn't run by default.
